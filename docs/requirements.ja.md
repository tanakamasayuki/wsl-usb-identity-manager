# 要件定義: WSL USB Identity Manager

*[English](requirements.md) | [日本語](requirements.ja.md)*

本書は本アプリケーションの要件を定義する。
根拠となる実測は [research-findings.ja.md](research-findings.ja.md)、
識別方式の設計は [identification-policy.ja.md](identification-policy.ja.md) に分離している。

---

## 1. 目的

Windows 上で `usbipd` を用いて WSL に USB デバイスを転送する運用において、
**「いま何が刺さっていて、それがどの物理デバイスなのか」を確実に把握できるようにする。**

単なる `usbipd` の GUI ラッパーではない。中核は **デバイスの継続的な同一性の追跡** である。

### 1.1 解決する問題

現行ツール（wsl-usb-gui）では以下が成立しない。

1. **シリアル番号を持たない同型デバイスを区別できない。**
   CH340 が 3 個あると、どれがどのボードか分からない。
2. **BUSID が信用できない。**
   BUSID は `Hub_#NNNN` + `Port_#MMMM` であり、`Hub_#NNNN` は Windows が
   ハブを認識した順に振る動的番号である（[F1](research-findings.ja.md#f1-usbipd-の-busid-は物理位置ではなく-windows-の動的ハブ番号)）。
   ハブの接続順や再起動で変化し、**同じ BUSID が別のデバイスを指すようになる。**
3. **COM 番号も `/dev/ttyUSB*` も接続状況で変わる。**
4. **デバッグプローブ（WCH-LinkE 等）は、プローブ自身が識別できても
   その先のボードが分からない。**

### 1.2 識別の対象範囲

USB シリアル変換アダプタやデバッグプローブは、**それ自体は識別できても、
その先に何が繋がっているかは分からない。**

- CH340 / CP210x / FTDI のシリアル番号は **アダプタ** を指すのであって、
  その先のボードを指さない。アダプタを別のボードに繋ぎ替えても番号は変わらない。
- WCH-LinkE のシリアル番号は **プローブ** を指すのであって、
  デバッグピンに繋がったボードを指さない。ボードを載せ替えても番号は変わらない。
- ESP32-S3 / C3 等のネイティブ USB 機種は、ボード自身が USB デバイスなので
  この問題が発生しない。

ユーザーが「このデバイス」と言うとき、多くの場合それは **アダプタやプローブではなく、
その先のボード** を指している。

> **本アプリケーションは、アダプタやプローブの先にあるボードまで識別することを
> 目的とする。**

#### 識別できる系統

先のボードまで識別できるのは、以下の 2 系統である。

| 系統 | 識別できるもの |
| --- | --- |
| **ESP32 系** | eFuse MAC によるボード個体 + チップ種別 |
| **CH32 RISC-V 系**（WCH-Link / WCH-LinkE の先） | 部品 UUID によるボード個体 + チップ種別 |

**要件 R1.1**: 上記以外のデバイスについては、アダプタ / プローブまでの識別に留める。
その場合、識別できているのがトランスポート層までである旨を UI 上で区別して示す。

**要件 R1.2**: 対応系統を後から追加できるよう、
系統ごとの識別処理を差し替え可能な単位に分離する。

### 1.3 中核となる設計思想

**「どこに接続されているか」と「それが何という物理デバイスなのか」を分離して扱う。**

| 分類 | 内容 | 扱い |
| --- | --- | --- |
| Runtime Connection | BUSID / COM 番号 / `/dev/ttyUSB*` / Attach 状態 | 表示のみ。識別子として使わない |
| USB Identity | VID/PID / USB シリアル / ポートパス | 毎回 Windows から取得する |
| Application Identity | プローブで得たボードの個体 ID | 実行中のみ保持し、切断で破棄する（§4.2） |
| User Metadata | ユーザー定義名称・メモ・Attach 設定 | 保存する（§7.1） |

保存するのは **ユーザーが決めたことだけ**である。
観測した事実は毎回観測し直す。理由は §4.1 と §7.1 に記す。

## 2. 責務分担

### 2.1 本アプリケーション（Windows 側）の責務

- Windows が認識している USB デバイスの列挙
- USB デバイスの識別情報の取得
- デバイスへの識別問い合わせ（プローブ）
- `usbipd` の状態取得と操作（Bind / Unbind / Attach / Detach）
- Attach 対象 WSL Distribution の管理
- ユーザー定義情報（名称・メモ・Attach 設定）の保存
- 接続・切断状態の監視と表示更新
- Windows 側状態と WSL への接続状態の統合表示
- 操作結果およびエラーの表示

### 2.2 WSL / Linux 側の責務（本アプリの責務外）

- `/dev/ttyUSB*` `/dev/ttyACM*` 等のデバイスノード管理
- udev によるデバイスイベント処理
- デバイスノードの権限管理、Linux グループ設定
- 安定したデバイス名の生成、シンボリックリンクの作成・削除
- Attach / Detach に連動した Linux 側処理

既存の [board-identify](https://github.com/tanakamasayuki/board-identify) による
WSL 内部のシンボリックリンク管理の仕組みは維持する。
**本アプリケーションはシンボリックリンクを生成・変更しない。**
取得できる場合に参照・表示するのみとする。

### 2.3 対象外

以下は本アプリケーションが扱わない。

- udev ルールの生成・管理
- WSL 内部のシンボリックリンクの生成・削除
- Linux のデバイス権限・グループ管理
- WSL 内アプリケーションの起動管理
- USB デバイス用 Linux ドライバの管理
- ファームウェア書き込み
- ESP32 等の開発環境管理

## 3. 状態モデル

### 3.1 3 層のアイデンティティ

§1.2 の通り、1 本のケーブルの先には最大 3 つの「もの」がある。
board-identify と同じ 3 層モデルで扱う。

| 層 | 内容 | 例 | 識別手段 |
| --- | --- | --- | --- |
| **Port** | 一時的な接続位置 | BUSID / COM8 / `/dev/ttyUSB2` | LocationPaths（永続化しない） |
| **Transport** | USB アダプタ / ブリッジ / プローブ | CH340, CH343, WCH-LinkE | USB Serial（無いこともある） |
| **Target** | その先のマイコンボード | ESP32-S3, CH32X035 | **プローブ**（§4.6） |

- ネイティブ USB のボード（ESP32-S3 等）では Transport と Target が同一になる。
- 生の USB シリアルアダプタに何も繋がっていない場合、Target は存在しない。
- **1 つの物理接続が Transport と Target の両方の識別子を同時に持ちうる**（R4.11）。

**要件 R3.1**: 一覧および詳細画面において、
表示している識別子が Transport のものか Target のものかを区別できること。

以降の §3.2〜§3.5 では、デバイスの状態を 4 つの情報群に分離して定義する。

### 3.2 USB Identity

物理 USB デバイスに由来する、Windows から取得できる情報。

| 項目 | 取得元 | 備考 |
| --- | --- | --- |
| VID / PID | Instance ID | |
| USB Serial Number | Instance ID 第 3 要素 | **無いデバイスがある**（CH340 等） |
| Manufacturer | `DEVPKEY_Device_Manufacturer` | |
| Product Name | `DEVPKEY_Device_BusReportedDeviceDesc` | USB の iProduct 文字列 |
| Windows Friendly Name | `DEVPKEY_Device_FriendlyName` | |
| Device Instance ID | `DEVPKEY_Device_InstanceId` | **usbipd との結合キー** |
| Container ID | `DEVPKEY_Device_ContainerId` | シリアル有りなら UUIDv5 で安定、無しなら UUIDv1 |
| バインド中ドライバ | `DEVPKEY_Device_Service` | どのドライバが付いているかの表示 |

### 3.3 Runtime Connection

現在の接続状態。**永続的な識別子として使用しない。**

| 項目 | 取得元 |
| --- | --- |
| 物理ポートパス | `DEVPKEY_Device_LocationPaths` |
| BUSID | `usbipd state` の `BusId`（未接続時は `null`） |
| Present / Missing | 列挙結果 |
| Shared / Not Shared | `usbipd state` の `PersistedGuid` |
| Attached / Detached | `usbipd state` の `StubInstanceId` / `ClientIPAddress` |
| Attach 先クライアント | `usbipd state` の `ClientIPAddress`（WSL 側の IP。Distribution 名は `usbipd` からは判らない） |
| COM ポート | レジストリ `Device Parameters\PortName`（**表示専用**） |

### 3.4 Application Identity

USB デバイスの先に存在する機器が提供する情報。プローブで取得する。

```text
Device ID          例: ESP32 の eFuse MAC、CH32 の部品 UUID
Device Type        例: esp32-s3, ch32x035c8t6
Hardware Revision
Firmware Version
Role
```

### 3.5 User Metadata

ユーザーが独自に管理する情報。Windows や USB が提供する情報が変化しても維持される。

```text
Alias（表示名）      必須
Memo                必須
Tags
用途 / 設置場所 / 管理番号
Default WSL Distribution
```

自動 Attach はデバイスごとの属性ではなく、
**条件の一覧**として持つ（§9）。同じ条件が複数のデバイスに一致しうるため、
デバイスの側に持たせると同じ設定が分散する。

## 4. デバイス識別

詳細は [identification-policy.ja.md](identification-policy.ja.md) を参照。本節は要件のみを記す。

### 4.1 識別の経路

| # | 経路 | 対象 | プローブ |
| --- | --- | --- | --- |
| 1 | USB シリアルによる Transport の識別 | シリアルを持つデバイス | **不要** |
| 2 | プローブによる Target の識別 | ボードに問い合わせられるデバイス | 要 |
| 3 | VID:PID + USB シリアルによる Target の識別 | 自前の VID:PID を持つボード | **不要** |

経路 1 で判るのは **Transport まで**である。アダプタやプローブ自身が名乗る
シリアル番号は、その先のボードを指さない（§1.2）。

経路 3 が経路 1 と違うのは、**VID:PID がボード自身のものである**と判る場合に限り、
同じシリアル番号が Target の識別子になる点である。アダプタは存在せず、
USB デバイスそのものがボードだからである。

**要件 R4.24**: ボード自身の VID:PID として登録されている組み合わせを持ち、
かつ USB シリアル番号を持つデバイスは、プローブなしで Target を識別する。
この経路はデバイスに何も送らないため、§4.3 の実行契機の制限を受けず、
副作用の提示（R4.7）も要らない。

> 対応表は board-identify から取り込む（`scripts/generate_board_ids.py`）。
> 表そのものは Arduino のボード定義に由来し、board-identify が集約している。
> 間に独自の加工を挟まないのは、**同じボードを 2 つのツールが違う名前で呼ぶ**
> のを避けるためである。
>
> この経路の答えは保持せず、必要になるたび Instance ID から導出する。
> 導出元が変わらない限り答えも変わらないため、保持する意味がない。
> Attach 中のデバイスにも答えられるのは、Instance ID が attach を越えて
> 残るためである（F4）。

**要件 R4.25**: 以下を機種名の決定に用いてはならない。

- 汎用 USB-UART ブリッジの VID:PID
- 複数のボードが名乗る VID:PID（系統は判るが、機種は決まらない）

> CH340 は ESP32 に載っていても素の AVR に繋がっていても CH340 である。
> その組み合わせが指すのはケーブルであり、シリアル番号もケーブルのものである。
> ボード定義の側が素のブリッジ ID を名乗ることは実際にあり
> （Sony Spresense は CP2102 の `10c4:ea60` を名乗る）、
> 表から消しても次の取り込みで戻る。よって参照時に拒否する。

**要件 R4.26**: 経路 2 と経路 3 の両方が答えられる場合、経路 2 を優先する。

> シリコンから読んだ値は、ディスクリプタを書き換える再書き込みを越えて残る。
> Espressif のボードは対応表から除外してあり、これも同じ理由による。

**要件 R4.1**: シリアルを持つデバイスは、そのシリアルを Transport の識別子として
表示しなければならない。Target の識別子として扱ってはならない。

**要件 R4.2**: 識別結果をポート位置や USB シリアルと結び付けて永続化し、
次回以降その対応関係から Target を推定してはならない。

> **なぜ推定してはならないか**
>
> USB シリアル変換は、USB 側が 1 バイトも変わらないまま別のボードに
> 繋ぎ替えられる。ポート位置も同様で、同じ口に別のボードを挿せば同じ値になる。
> したがって「前回このポート／このシリアルの先にあったボード」から今回のボードを
> 導くことはできない。**導けば、確信を持って誤った名前を表示する。**
> それは何も表示しないより悪い。

### 4.2 識別結果の寿命

**要件 R4.3**: Target の識別結果は、そのデバイスが接続されている間だけ保持する。
デバイスが取り外された時点で破棄しなければならない。

ケーブルの先が変わりうる唯一の瞬間が取り外しである。WSL への Attach / Detach は
物理的な取り外しではないため、識別結果を破棄しない。

**要件 R4.4**: 未識別のデバイスと識別済みのデバイスを UI 上で区別できること。
推測した識別結果を、問い合わせて得た識別結果と同じ形で表示してはならない。

**要件 R4.21**: 最後に識別できた結果を「最終識別」として参考表示する。
確定情報とは視覚的に区別し、確定情報として扱ってはならない（R4.4）。
識別した日時を併記する。

> 取り外しで識別結果を破棄する（R4.3）のは、ケーブルの先が変わりうるためである。
> だがそれは「変わったかもしれない」であって「変わった」ではない。
> 直前まで判っていたことまで消すと、挿し直しただけのデバイスが、
> 一度も識別したことのないデバイスとまったく同じ見た目になる。
> 参考値として残せば、どちらの問いにも答えられる。
>
> 日時を併記するのは、この値が再起動を跨いで残るためである（R4.23）。
> 「何だったか」は「いつのことか」と並べて初めて判断材料になる。

**要件 R4.23**: 最終識別は保存し、再起動後も参考表示する。

> WSL へ Attach 中のデバイスはプローブできない（F4）。
> 保存しなければ、ボードを Attach したままの状態で起動した PC は、
> どれがどれなのかを最後まで答えられない。
> Detach して識別し直すまで判らない、では本アプリの目的を果たさない。

**要件 R4.22**: 最終識別の情報は以下に用いてはならない。

- 自動 Attach の判定（R4.6、§9）
- 確定情報としての復元。読み戻した値は常に参考値である。

> 参考表示は人に向けた材料であって、機械の判断材料ではない。
> シリアル無しデバイスの Instance ID はポート由来であるため、
> 同じポートに別のボードを挿せば前のボードの識別結果が残ったままになる。
> 人が見て「違う」と判断できる場所に置くのはよいが、
> それを根拠に WSL へ引き渡してはならない。

### 4.3 プローブの実行契機

プローブには副作用がある。`esptool` 系はボードを再起動させ、
WCH-Link の attach はターゲットのコアを一時停止させる。

**要件 R4.5**: プローブを実行してよいのは以下の 2 契機に限る。

1. **ユーザーが明示的に「識別」を指示したとき**
2. **接続直後の猶予時間内**（§4.4。設定で無効にできる）

**要件 R4.6**: 以下ではプローブを実行してはならない。

- 定期ポーリング
- 一覧画面の更新
- アプリ起動時の一括スキャン
- 自動 Attach の判定

**要件 R4.7**: プローブ実行前に、副作用（対象が再起動する等）をユーザーに提示する。

### 4.4 接続直後の自動識別

**要件 R4.8**: 接続された直後のデバイスを自動で識別する機能を提供する。

| 設定項目 | 既定値 |
| --- | --- |
| 自動識別の有効化 | 有効 |
| 対象 | シリアルを持たないデバイスのみ |
| 猶予時間 | 接続イベントから 10 秒以内 |
| 除外する VID/PID | ユーザーが列挙（既定は空） |

シリアルを持つデバイスを対象外とするのは、その多くがネイティブ USB のボード自身で、
Transport と Target が同一であり、問い合わせずとも判るためである。

> **この規則には穴がある。** シリアルを持つ *アダプタ*（CH343 等）や
> **WCH-Link** の先にあるボードは、依然として問い合わせなければ判らない。
> これらは自動識別の対象から外れ、手動で識別するまで未識別のままになる。
> 自動で再起動・停止させる対象を絞ることを優先した結果であり、
> 見落としとしてではなく選択として記録する。
> 一括識別（R4.19）がこの穴を埋める手段である。

**要件 R4.9**: 除外された VID/PID のデバイスへ、自動でデータを送信してはならない。

> **許可リストではなく除外リストである理由**
>
> 「対象とする VID/PID を列挙する」方式は機能しない。CH340 の VID/PID は、
> その先が開発ボードかルータのコンソールかを何も語らないため、
> 許可リストを作ると結局よく使われるブリッジを全て並べることになり、
> 除外リストと同じ効果を回りくどく実現するだけである。
> 触られては困る機器を名指しする方が、実態に合う。

**要件 R4.19**: 接続中の未識別デバイスを**まとめて識別する**操作を提供する。
自動識別の対象外となったものを、利用者が 1 操作で識別できること。

**要件 R4.20**: 猶予時間内は、プローブを実行できるようになるまで再試行する。

> デバイスが Windows に見えてから COM ポートが割り当てられるまでには間がある。
> 到達した瞬間に 1 度だけ判定すると、自動識別はたいてい負ける。
> 試行の上限を与えるのは猶予時間であって、最初の 1 回ではない。

### 4.5 識別子フォーマット

識別子は **本アプリケーション内部のもの**であり、
外部ツールとの互換性は要求しない。
形式は board-identify の実績ある規則を踏襲する。

```text
<variant>-<unique-id>

esp32-s3-7cdfa1123456
ch32x035c8t6-1ff9abcd880ebc48
wch-link-fc928f068181
```

規則: 小文字 ASCII / 区切りは `-` / unique-id から記号を除去 /
6 文字未満の unique-id は不採用 / `/` と NUL を含まない。

**要件 R4.10**: 識別子の生成は決定論的でなければならない。
同一の入力（チップ種別と固有 ID）に対して常に同一の文字列を返すこと。

**一度リリースした後に生成規則を変更してはならない。**

> 識別子は画面に表示され、利用者がメモや他ツールとの突き合わせに使う。
> 規則が変われば、同じ機器が別物の名前で現れる。
> アプリが保存していないからこそ、**外に出た文字列を直す手段が無い。**

**要件 R4.27**: チップ種別の名前は board-identify と一致させる。
一致しない場合は、**こちらを合わせる**。

> 同じボードが 2 つのツールで別の名前になれば、突き合わせは不可能になる。
> どちらが正しいかではなく、**1 つであること**に価値がある。
>
> 具体的には、初代 ESP32 のチップ名は esptool の
> `ESP32ROM.get_chip_description()` に従う（`ESP32-D0WD-V3` 等）。
> 使用している espflash はシリーズ名（`esp32`）までしか返さないため、
> パッケージを示す eFuse を 1 ワード追加で読んで補う。
> ESP32-S2 以降はシリーズ名がそのままチップ名であり、差は生じない。

**要件 R4.11**: 1 つのデバイスが複数の識別子を同時に持ちうる。
デバッグプローブの場合、プローブ自身とその先のボードの両方を保持する。

### 4.6 プローブの対象と手段

Transport（アダプタ / プローブ）の識別は USB 記述子だけで済むが、
**Target（その先のボード）の識別にはプローブが要る。**

#### Target まで識別できる系統

| 系統 | 手段 | 得られる Target ID | 前提 |
| --- | --- | --- | --- |
| **ESP32 系**（CH340 / CP210x 等の裏） | シリアル経由の ROM ブートローダ通信、eFuse MAC 読み出し | MAC アドレス + チップ種別 | COM ポートが開けること |
| **CH32 RISC-V 系**（WCH-Link の先） | WCH-Link のベンダプロトコル | 部品 UUID + チップ署名 | プローブが RISC-V モードであること |

CH32 系の取得手順は `ch32rv-wchlink` の以下の呼び出しで完結する。

```rust
WchLink::open(&UsbDeviceInfo)   // RISC-V モード (1a86:8010) の interface 0
  .probe_info()      -> ProbeInfo        // プローブ自身の情報
  .set_speed_default(Speed)              // 任意。R4.16 を参照
  .attach_chip()     -> AttachInfo       // family + chip_id（上位 4bit = シリコン改訂）
  .chip_info()       -> ChipInfoStatus   // flash_kb, uuid: [u8; 8], protection_raw
  .detach_chip()
```

- **Target の個体識別子** = `ChipInfo.uuid`（8 バイトの工場出荷時 UUID）
- **Target のチップ種別** = `AttachInfo` の family / chip_id を
  `ch32rv-target` の `Db` で SKU へ解決する
- `attach_chip()` はターゲットのコアを停止させるため、副作用のあるプローブである（R4.5）

**要件 R4.15**: WCH-Link が ARM モードの場合、RISC-V モード用の
VID/PID では開けない。モードを検出し、切り替えが必要である旨を案内する。
**アプリがモードを自動で切り替えてはならない。**

**要件 R4.16**: `set_speed` の失敗を識別の失敗として扱ってはならない。

> デバッグリンクの速度設定は性能のヒントであり、識別には要らない。
> 初代 WCH-Link（CH549 ベース、firmware 2.6 で実測）はこのコマンドを実装しておらず、
> attach の前後いずれで送っても `82 81 01 ff` を返す。
> これを必須にすると、動作するはずの識別が丸ごと失敗する。

**要件 R4.12**: WCH-Link への接続に、WinUSB ドライバの割り当てを要求してはならない。

> WCH-Link の interface 0 には、WCH 純正ドライバ（`WCHLink_A64`）が当たっているのが
> 通常の状態である。`ch32rv-usb` は nusb での claim に失敗すると、Windows では
> CH375 系の `DeviceIoControl` へ自動でフォールバックするため、
> **純正ドライバのままプローブできる**（実測）。
> ドライバの差し替えを求めれば、ユーザーに Zadig 等の操作を強い、
> かつ WCH-Link のシリアルポート機能を失わせることになる。
> **アプリがドライバを差し替えてはならない。**

#### プローブが不要な場合

| 対象 | 理由 |
| --- | --- |
| ESP32-S3 / C3 等（ネイティブ USB） | Transport と Target が同一で、MAC が USB シリアルとして露出している |
| USB シリアルを持つアダプタ自体 | 記述子だけで Transport を識別できる |

#### 対応外の系統

上記以外（Arduino、RP2040、STM32、汎用の CH340 の先にある不明なボード等）は、
**Transport までの識別に留まる。**

**要件 R4.13**: 対応外の系統では Target の識別を試行しない。
未対応であることを UI 上で示し、ユーザーが Alias で補えるようにする。

ただし、汎用の USB シリアル変換の先に何があるかは記述子から判らないため、
「対応外である」と事前に判定できるのは **VID/PID で系統が特定できる場合に限る**。
それ以外は試行して応答が無いことで判明する（§4.7）。

### 4.7 プローブの優先順位

**要件 R4.17**: 各プローブは、対象デバイスを **VID/PID で特定できるか**を宣言する。

| 種別 | 意味 | 例 |
| --- | --- | --- |
| 識別子による特定 | VID/PID でハードウェアが判る。何も触らずに判定できる | CH32 系（WCH-Link） |
| フォールバック | 形が合うだけ。先に何があるかは問い合わせるまで判らない | ESP32 系（COM ポート） |

**要件 R4.18**: 識別子で特定できるプローブが対象デバイスを自分のものと認めた場合、
フォールバックのプローブを実行してはならない。

「認めた」には、実行できない状態（ARM モードの WCH-Link 等）も含む。
ARM モードであっても WCH-Link であることに変わりはなく、
ESP32 用のリセットと同期信号を送ってよい相手ではない。

> **フォールバック側に除外リストを持たせてはならない。**
> WCH-Link はシリアルポートを持つため、汎用のシリアルプローブからは
> アダプタと区別がつかない。これを「ESP32 プローブが除外する VID/PID」として
> 表現すると、系統が増えるたびにその除外リストが伸び続ける。
> 優先順位で表現すれば、新しい系統は自分の VID/PID を名乗るだけで済む。

**要件 R4.14**: 系統の追加が、識別処理の追加のみで完結する構造とする
（既存の系統の処理に手を入れる必要がないこと）。

## 5. usbipd 連携

### 5.1 結合キー

**要件 R5.1**: `usbipd` との対応付けには `usbipd state` が返す
`InstanceId` を用いる。BUSID を対応付けに使用してはならない。

**要件 R5.2**: `usbipd` の状態取得には `usbipd state`（JSON）のみを使用する。
`usbipd list` のテキスト出力をパースしてはならない。

**要件 R5.3**: Attach 中のデバイスは `StubInstanceId`
（`Vid_80EE&Pid_CAFE\<元の第3要素>`）で追跡する。

### 5.2 操作

GUI から以下を実行できること。

| 操作 | コマンド | 権限 |
| --- | --- | --- |
| Bind（共有） | `usbipd bind --busid <BUSID>` | **管理者** |
| Unbind | `usbipd unbind --busid <BUSID>` | **管理者** |
| Unbind（未接続） | `usbipd unbind --guid <PersistedGuid>` | **管理者** |
| Attach | `usbipd attach --busid <BUSID> --wsl <DISTRO>` | 一般 |
| Detach | `usbipd detach --busid <BUSID>` | 一般 |
| 状態更新 | `usbipd state` | 一般 |

**要件 R5.4**: BUSID は操作を発行する直前に `usbipd state` から取得した値を用いる。
記録した BUSID を再利用してはならない。

**要件 R5.5**: 操作対象のデバイスを、ユーザーが識別情報を確認した上で選べること。

**要件 R5.11**: 未接続のデバイスに対して BUSID を要する操作を提示してはならない。

共有の記録はデバイスが無くなっても残るため、
**未接続のデバイスに対して意味があるのは Unbind だけ**である。
このとき BUSID は存在しないので、`usbipd` が記録を指すために用意している
`--guid` で指定する。

> `PersistedGuid` を識別子として保存してはならない（R7.1）という制約と矛盾しない。
> ここでの用途は、操作の直前に `usbipd state` から読んだ値を
> そのコマンドに渡すだけであり、R5.4 と同じ扱いである。

### 5.3 権限設計

**要件 R5.6**: アプリケーション本体は非昇格で起動する。
管理者権限が必要な操作の実行時にのみ、
`ShellExecuteExW(verb="runas")` で `usbipd.exe` を昇格実行し、
終了コードを取得して結果を判定する。

**要件 R5.10**: 昇格実行のコマンドラインへ値を埋め込む前に、
その値が期待する形式（BUSID は `<数字>-<数字>`）であることを検査する。
検査を通らない値では実行しない。

> 昇格プロセスのコマンドラインは、`CreateProcess` のように
> 引数を配列のまま渡せない。文字列として組み立てる以上、
> 何が入りうるかを呼び出す側で閉じておく。

**要件 R5.7**: 初期設定として `usbipd policy add`（AutoBind）の設定を
支援する導線を提供する。これにより日常運用での昇格頻度をほぼゼロにできる。

### 5.4 環境依存の警告

**要件 R5.8**: `usbipd` が出力する警告（USB フィルタドライバとの非互換など）を
検出し、`bind --force` が必要な状況をユーザーに提示する。

**要件 R5.9**: `bind --force` は Windows からデバイスを取り上げるため、
プローブと両立しない。この制約を UI 上で明示する。

## 7. データモデルと永続化

### 7.1 保存する情報

保存するのは**ユーザーが決めたこと**と、
**参考値であると明示したもの**だけである。
アプリが観測した事実（列挙結果、識別結果、usbipd の状態）を、
事実として保存してはならない。次回の起動時にもう一度観測すればよく、
保存すれば「前回はこうだった」が「今もこうである」に化けるためである。

最終識別（R4.21）はその「化ける」経路を塞いだ上で保存する。
読み戻した値は常に参考値として表示され、
自動 Attach の判定には一切用いない（R4.22）。

```text
Settings（アプリ全体）
  auto_identify            接続直後に自動で識別する（§4.4）
  auto_exclude             自動識別から除外する VID:PID の一覧
  confirm_before_identify  識別の副作用を実行前に確認する（§4.3）
  start_with_windows       Windows へのサインイン時に起動する
  auto_attach              自動 Attach の有効／無効（§9）
  auto_attach_rules        自動 Attach の条件（種類 + 値。R9.1）
  told_about_tray          閉じてもトレイに残ることを一度説明したか（R10.15）

User Metadata（対象ごと。§3.5）
  key                      R7.7 のキー
  alias / memo / tags
  default_wsl_distribution

LastSeen（デバイスごと。参考値。R4.21 / R4.23）
  instance_id              見かけたときの Device Instance ID
  name                     Windows が記述できていたときの名前（R10.23）
  identity                 最後の識別結果
  identified_at            その識別を行った日時
```

**要件 R7.7**: User Metadata のキーは、USB シリアルがあればそれを用い、
無ければポートパス（`DEVPKEY_Device_LocationPaths`、F2）を用いる。

ポートパスをキーにしたメタデータは、
**そのポートに挿したものに対する注記**であって、特定の個体に対する注記ではない。
挿し替えれば別の機器に付く。UI はこの違いを示す（R4.4）。

### 7.2 永続化してはならない情報

**要件 R7.1**: 以下を識別子として永続化してはならない。

- BUSID
- COM 番号（表示用の参考値としての保持は可）
- `/dev/ttyUSB*` 等の Linux デバイスノード
- `usbipd` の `PersistedGuid`（usbipd 内部の識別子であり、
  シリアル無しデバイスではポートに紐づくため）

**要件 R7.8**: プローブで得た Application Identity（§3.4）を、
**確定情報として**保存してはならない。確定した識別結果は実行中のみ保持し、
切断で破棄する（R4.2 / R4.3）。保存してよいのは参考値としての最終識別だけであり
（R4.21 / R4.23）、読み戻した値を確定情報に昇格させてはならない（R4.22）。

**要件 R7.9**: 保存する最終識別には件数の上限を設け、
上限を超えたときは最後に見てから最も古いものから捨てる。
また、利用者がすべて消去できること。

> ボードは増えるよりもポートを渡り歩く。上限が無ければ、
> 一度挿しただけのポートの記録が際限なく積み上がる。
> 消去手段が要るのは、この部分だけは**何も壊れていないのに間違いうる**ためである。
> ボードを別のポートへ移せば、前の記録はその場に残り続ける。

### 7.3 保存場所

**要件 R7.2**: 実行ファイルと同じディレクトリに `portable.txt` が存在する場合は
そのディレクトリに、存在しない場合は `%APPDATA%` 配下に保存する。

### 7.4 形式とスキーマ版

**要件 R7.3**: 保存形式は人間が読めるテキスト形式（JSON）とする。
ポータブル運用で設定を持ち運べること、
問題発生時に中身を確認できることを優先する。

**要件 R7.4**: ファイルの先頭にスキーマ版を持つ。

```json
{ "schema_version": 1, "settings": { ... } }
```

**要件 R7.5**: 読み込み時にスキーマ版を検査する。

- 既知の古い版 → 移行してから使用し、移行前のファイルを退避する
- **未知の新しい版 → 読み込まず、上書きもしない。**
  新しい版のアプリで作られた設定を古いアプリが破壊しないこと

**要件 R7.6**: 保存は書き込み中の中断でファイルが壊れない方法で行う
（一時ファイルへ書いてから置換する）。

## 8. デバイス監視

**要件 R8.1**: 以下の状態変化を検出し、表示を更新する。

- Windows への USB 接続 / 切断
- `usbipd` の Bind 状態変更
- WSL への Attach / Detach

**要件 R8.2**: デバイス列挙とプロパティ取得には `CfgMgr32` / `SetupAPI` を
ネイティブに呼び出す。PowerShell の PnP コマンドレットを使用してはならない
（実測で 700 倍以上の性能差がある。[F7](research-findings.ja.md#f7-windows-pnp-へのアクセスは-powershell-経由では実用にならない)）。

**要件 R8.3**: ホットプラグ通知には `CM_Register_Notification` または
`WM_DEVICECHANGE` を用いる。定期ポーリングを主たる検出手段としない。

**要件 R8.4**: 「接続された」の判定には、Windows のデバイスノードへ
**到達できるか**を用いる。`usbipd state` の `BusId` の有無で判定してはならない。

> Attach 中も `usbipd` は BUSID を報告し続ける（実測）。
> これを接続の有無とみなすと、Attach / Detach で値が変わらず、
> 逆に Windows から触れない間を「接続中」と誤って扱うことになる。

## 9. 自動 Attach

条件に一致したデバイスを、ユーザーの操作なしに WSL へ接続する。

### 9.1 条件の種類

**要件 R9.1**: 自動 Attach の条件は、以下の 4 種類のいずれかで指定する。

| 種類 | 何を指すか | 安定性 |
| --- | --- | --- |
| **ボード ID**（識別子） | ボード自身が答えた ID（§4.5） | ボードに付いて回る。**識別済みのときだけ判る** |
| **USB シリアル** | その USB デバイス自身 | 安定。ただしアダプタの先のボードは指さない（§1.2） |
| **VID/PID** | その種類のデバイスすべて | 安定。「CH340 は全部」という指定 |
| **BUSID** | その BUSID にあるもの | **安定しない**（F1） |

**要件 R9.2**: 各条件がどの層を指しているか（§3.1）を UI 上で示す。

**デバイス名（Description）による一致は提供しない。**

> デバイス名は Windows / USB 記述子が返す文字列であり、
> **同じ型番のデバイスはすべて同じ名前になる。**
> つまり VID/PID より粗い条件にしかならないうえ、
> ドライバの差し替えや COM 番号の混入で変化しうる。
> VID/PID を選べる以上、名前で一致させる意味がない。

> BUSID は、ハブを挿すだけで振り直される（F1）。
> それでもこれを条件として提供するのは、
> 「この口に挿したものを WSL に送る」という指定に実用があるためである。
> **提供したうえで、何を指しているのかを明示する。**

**要件 R9.3**: 複数の条件が一致する場合、
**より具体的な種類**（上の表の上から順）を一致した条件として扱う。

### 9.2 実行条件

**要件 R9.4**: 自動 Attach の判定のためにプローブを実行してはならない（R4.6）。

条件の照合に使う値は、いずれも列挙済みの情報から得られる。
ボード ID による条件は、**識別済みのデバイスにのみ一致する**。
識別されていなければ、その条件は一致しないまま待つ。

**要件 R9.5**: 自動 Attach を実行してよいのは、以下をすべて満たす場合に限る。

- 自動 Attach が有効であること
- 条件に一致すること
- **`usbipd` で共有済み（bound）であること**
- Windows から見えていること（R8.4）

> 共有には管理者権限が要る（§5.3）。
> 一度も共有していないデバイスを自動で共有しにいけば、
> ユーザーが何もしていないのに UAC のダイアログが出ることになる。
> **自動処理が昇格を要求してはならない。**

**要件 R9.6**: 識別の対象になっているデバイスは、識別が終わるまで Attach しない。

> Attach すると Windows からデバイスが見えなくなり、プローブできなくなる。
> 先に Attach してしまえば、ボード ID の条件が待っている答えを
> 永久に得られなくする。

**要件 R9.7**: 1 台への自動 Attach は、接続が検出されてから 1 度だけ試行する。
失敗しても、取り外して挿し直すまで再試行しない。

> 2 秒ごとに再試行すれば、失敗し続けるデバイスが
> エラーを出し続けることになる。
> また、ユーザーが手動で Detach した直後に自動 Attach が復活すれば、
> **アプリがユーザーの操作を取り消すことになる。**
> Attach / Detach ではこの記録を消さず、物理的な取り外しでのみ消す。

**要件 R9.8**: 自動 Attach は 1 台ずつ順に実行する。

### 9.3 操作

**要件 R9.9**: 自動 Attach の有効／無効を、**メイン画面から 1 操作で**切り替えられること。

> 「いまは Windows 側で使いたい」は作業中に起きる。
> 設定ダイアログを開かせるべきではない。

**要件 R9.10**: 条件の一覧を表示・追加・削除できる画面を提供する。
各条件が現在何台に一致しているかを示す。

**要件 R9.11**: デバイスを選択した状態で、そのデバイスが提供する値
（R9.1 の 4 種類のうち、実際に持っているもの）から
**1 つを選んで条件にできること。** 選択は排他とし、「なし」を選べること。

**要件 R9.12**: 選択によって削除される条件が他のデバイスにも一致していた場合、
その旨を示す。

> VID/PID の条件はそのデバイスだけのものではない。
> 1 台の画面での操作が他の台の挙動を変えたことは、黙って起こしてはならない。

**要件 R9.13**: 自動 Attach の条件に一致しているデバイスを一覧上で判別できること。
自動 Attach が無効なときも一致は示し、**実行されないことが判る表示**にする。

> 条件を組み立てている最中は、まだ有効にしていないことが多い。
> 「いま何に一致しているか」が見えなければ、条件を作るのは当て推量になる。

## 10. ユーザーインタフェース

### 10.1 メイン画面（デバイス一覧）

Windows が列挙している USB デバイスと、`usbipd` が記録しているデバイスを
**1 つのリスト**に表示し、状態でのフィルタを上部に置く。

> 状態ごとにテーブルを分けると、Attach した行がテーブル間を飛び、
> ちょうど見ている最中に消える。1 つのリストなら行はその場に留まり、
> 状態表示だけが変わる。

| 列 | 内容 |
| --- | --- |
| 状態 | Shared / Attached（§5.2） |
| 接続 | Windows から到達できるか。BUSID とポート |
| デバイス | Windows / USB の認識名。**識別しても書き換えない** |
| VID:PID | ベンダ名を併記（§10.5） |
| USB シリアル番号 | USB Serial Number。無い場合はその旨を示す（Transport 層、§3.1） |
| ボード | 識別結果、または未識別（Target 層。§4.2、R4.4） |
| 自動 | 自動 Attach の条件に一致しているか（R9.13） |

**要件 R10.12**: 列の見出しには、**そのセルに何が入っているか**を書く。
§3.1 の層の名前（Port / Transport / Target）をそのまま見出しにしない。

> 「Transport」は設計上の層の名前であって、利用者の語彙ではない。
> セルに入っているのは USB のシリアル番号であり、そう書けば説明が要らない。
> 層の区別は、見出しではなくツールチップと詳細画面が担う。
>
> 「番号」まで書くのは、本アプリが扱う対象がほぼ全て USB シリアル変換であり、
> 「シリアル」だけでは**シリアル回線**と読めてしまうためである。

**要件 R10.1**: Windows から見えないデバイス（Attach 中、または
`usbipd` の記録のみ）も一覧に表示し、接続中のものと区別できること。

**要件 R10.2**: 識別できる系統の未識別デバイスでは、
「識別」操作への導線を行内に置く。

**要件 R10.7**: 識別結果でデバイス名を書き換えてはならない。
Windows / USB の認識名はそのまま残し、識別結果は別の列に示す。

> 名前が書き換わると、その行が Windows のどのデバイスなのかが判らなくなり、
> `usbipd` や USBTreeView の表示と突き合わせられなくなる。

**要件 R10.23**: Windows がデバイスを記述できなくなった場合、
直前に取得できていた名前を参考表示する。確定情報とは視覚的に区別し、
現在の名前を置き換えるのではなく併記する（R10.7）。

> WSL へ Attach したデバイスは VBoxUSB スタブとして再列挙されるため、
> Windows 側の名前は失われる（F4）。`--force` を伴う bind でも同じことが起きる。
> 代わりに `usbipd` がキャッシュしている説明が出るが、
> キャッシュがドライバ差し替え後に取られていればそれも汎用名である。
> 共有した途端に行から個体が判らなくなるのは、本アプリが避けるべき状態そのものである。

### 10.2 詳細画面

§3.2〜§3.5 の 4 情報群を分けて表示する。

```text
USB Identity        VID / PID / Serial / Manufacturer / Product /
                    Instance ID / Location Path / Driver Service
Application Identity Device ID / Device Type / HW Revision / FW Version / Role
User Metadata       Alias / Memo / Tags / Default WSL
Runtime Connection  BUSID / COM / Shared / Attached / Attach 先クライアント
WSL State           デバイスノード / シンボリックリンク（参照のみ）
```

あわせて、選択中のデバイスに対する操作を置く。

- `usbipd` の操作（§5.2）と識別（§4.3）
- **自動 Attach の条件の選択**（R9.11）

**要件 R10.22**: 本アプリのバージョンを UI 上で確認できること。
ログの出力先と同じ場所に置く。

> バージョンとログは、不具合を報告するときに両方要る。
> 別々の場所を探させる理由がない。
> 値は `Cargo.toml` の唯一の版から取る（R12.4）。

**要件 R10.13**: 詳細画面の値は選択してコピーできること。

> ここに出ている値は、`usbipd` のコマンドや issue に貼るためのものである。
> 読めても取り出せなければ、結局手で書き写すことになる。

### 10.3 設定画面

- 記憶しているデバイスの件数と、その消去（R7.9）
- 接続直後の自動識別と、その除外リスト（§4.4）
- 識別前の副作用確認の有無（§4.3）
- Windows へのサインイン時の自動起動
- 既定の WSL Distribution
- 表示言語（§10.4）

自動 Attach の有効／無効と条件は、**この画面には置かない**。
切り替えはメイン画面（R9.9）、条件は専用画面（R9.10）が扱う。

**要件 R10.8**: 設定が保存できない状態（R7.5 で読み込みを拒否した場合等）では、
その旨を設定画面に示す。保存されない設定は、保存されると誤解される方が害が大きい。

### 10.4 多言語対応

**要件 R10.3**: 起動時に OS の表示言語を取得し、
対応言語があれば自動的にその言語で表示する。

**要件 R10.4**: 設定画面で表示言語を明示的に選択できること。
選択肢は「システムに従う（既定）」と、対応する各言語。

**要件 R10.5**: UI 文字列の原本は英語とする。
翻訳リソースは言語ごとのファイルに分離し、
未翻訳の項目は英語にフォールバックする。

**要件 R10.6**: 対応言語は英語と日本語とする。
言語の追加が翻訳ファイルの追加のみで済む構造にする。

**要件 R10.9**: 識別処理が返すメッセージは翻訳キーを伴う。
英語の文面そのものを照合して翻訳してはならない。
文面を直した瞬間に翻訳が外れるためである。

### 10.5 ベンダ名の表示

VID / PID の数値だけでは製造元が判らないため、
[USB ID Repository](http://www.linux-usb.org/usb-ids.html) の `usb.ids` を参照して
ベンダ名・製品名を併記する。

**要件 R10.10**: `usb.ids` を本アプリの配布物に同梱しない。
`usbipd-win` のインストール先（`usbipd.exe` と同じディレクトリ）にあるものを読む。

> 同梱は再配布であり、`usb.ids` のライセンス条件の確認を伴う。
> 本アプリは `usbipd-win` を前提としており、
> そちらが同じファイルを同じ目的で置いている。読むだけで足りる。

**要件 R10.11**: `usb.ids` が見つからない場合も動作を継続する。
ベンダ名の欄が空になるだけとし、エラーにしない。

> 登録されていないベンダは珍しくなく、
> 未登録と参照不能を利用者が区別する意味もない。

### 10.6 常駐とウィンドウの扱い

自動 Attach（§9）と接続直後の自動識別（§4.4）は、
**プロセスが動いている間しか効かない。**
ウィンドウと一緒に終了すれば、設定した条件は何もしないまま消える。

**要件 R10.14**: ウィンドウを閉じても終了せず、通知領域に常駐する。
終了はトレイアイコンのメニューから行う。

**要件 R10.15**: 初めて閉じたときに一度だけ、
**終了ではないこと**と、終了する手段を示す。以後は表示しない。

> これを言わないと、閉じたつもりのアプリが背後で自動 Attach を実行し、
> 接続直後の自動識別でボードを再起動させる。
> 毎回言えば邪魔になるので、一度だけ言って記録する（`told_about_tray`）。

**要件 R10.16**: トレイのメニューには以下を置く。

| 項目 | 内容 |
| --- | --- |
| 状態 | 接続中 / 共有 / WSL 接続中 の台数（クリック不可） |
| 自動 Attach | ON / OFF の切り替え（R9.9 の経路のひとつ） |
| 一括識別 | 接続中の未識別デバイスをまとめて識別する（R4.19）。対象が無ければ選べない |
| 開く | ウィンドウを表示する。アイコンの左クリックでも同じ |
| 設定 | ウィンドウを表示し、設定画面を開く |
| 終了 | アプリケーションを終了する |

**要件 R10.17**: トレイのラベルは UI と同じ翻訳から作る。
バックエンドに文字列のカタログを持たせない（R10.5）。

**要件 R10.20**: トレイから実行した一括識別も、識別前の確認設定（R4.7）に従う。
確認が必要な場合はウィンドウを表示してから尋ねる。

> 確認のダイアログはウィンドウの中にある。
> 隠れたまま尋ねれば、誰も見ていないダイアログの前で処理が止まる。

**要件 R10.21**: 実行中はトレイの状態行に進捗を出す。

> ウィンドウを閉じたまま一括識別を始められる以上、
> 「ボードが順に再起動しているが画面には何も出ない」時間ができる。

**要件 R10.18**: 自動起動（§7.1）で起動した場合は、
**ウィンドウを開かず**通知領域に入る。

> サインインは「ウィンドウを見せろ」という指示ではない。
> 自動 Attach のために常駐させている利用者にとって、
> 毎回ウィンドウが開くのは邪魔でしかない。

**要件 R10.19**: 常駐中に本アプリをもう一度起動した場合、
**隠れているウィンドウを表示して前面に出す**（R13.10）。

## 11. 技術スタック

| レイヤ | 採用 |
| --- | --- |
| 言語 | Rust |
| GUI | Tauri 2（WebView2） |
| デバイス列挙・プロパティ | `windows` crate → `CfgMgr32` / `SetupAPI` |
| USB 生アクセス | `nusb`（`ch32rv-usb` 経由。直接依存しない） |
| シリアル | `serialport` |
| WCH-Link プローブ | [ch32rv](https://github.com/ch32-riscv-ug/ch32rv) の crate（`ch32rv-wchlink` / `ch32rv-usb` / `ch32rv-target`） |
| ESP32 プローブ | `espflash` crate |

> **GUI に Tauri（WebView2）を用いる根拠**
>
> - 一覧・詳細ペイン・設定画面という UI は、HTML/CSS が最も実装量が少ない。
> - Alias / Memo に日本語を入力する（§3.5）ため、IME が確実に動くことが要る。
>   WebView2 は OS のテキスト入力機構そのものである。
> - 日本語表示に追加フォントの同梱が要らない。OS のフォントを使う。
>   Rust 製のネイティブ GUI は、任意の漢字が入る以上 subset できず、
>   CJK フォント（5〜8 MB）の同梱が必要になる。
>
> 代償は WebView2 への依存であり、§11.2 の通り検出でき、欠落は例外的である。

### 11.1 役割分担

**要件 R11.1**: デバイスの列挙と識別情報の取得は `CfgMgr32` が担当する。
`nusb` による列挙はプローブの内部事情であり、一覧の情報源にしてはならない。

> `nusb` は Windows において、デバイス全体が特定ドライバにバインドされている場合に
> シリアル番号を取得できない。CH340（`CH341SER_A64`）が該当する。
> `CfgMgr32` は Instance ID / LocationPaths / ContainerId / Service を返すため、
> 情報量でも上回る（F3）。

### 11.2 WebView2

**要件 R11.2**: 起動時に WebView2 Runtime の有無を確認する。
未導入の場合はダウンロード先を案内して終了する。

以下のいずれかが存在し、`pv` が `0.0.0.0` 以外であれば導入済みである。

```text
HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}\pv   per-machine
HKCU\Software\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}\pv                per-user
```

- Windows 11 は OS に同梱する。
- Windows 10 は「大多数の端末に導入済み」と Microsoft が明記している。
  例外として Windows Server、LTSC、Windows Update から切り離された端末がある。
- 導入は Evergreen Bootstrapper（約 2 MB、
  `MicrosoftEdgeWebview2Setup.exe /silent /install`）で行える。
  Fixed Version（250 MB 超）は採用しない。

インストーラ版は NSIS の `webviewInstallMode`（`downloadBootstrapper`）が
インストール時に解決するため、この検査は主にポータブル版のためのものである。

### 11.3 ch32rv への依存方針

**要件 R11.3**: ch32rv の crate は **crates.io 公開版に依存する。**
git 参照や vendoring は行わない。

```text
ch32rv-wchlink   WCH-Link プロトコル
ch32rv-usb       プローブの列挙とオープン（nusb ラッパ、CH375 フォールバック付き）
ch32rv-target    チップ ID → SKU 解決の DB
```

`serialport` は ch32rv の workspace が固定している版に合わせる。
espflash と同じ crate を共有するため、版が割れると両方が壊れる。

#### 0.x 系への依存に対する扱い

ch32rv は 1.0 到達前であり、**API の変更が想定されている。**
Cargo の semver では `0.7` → `0.8` は破壊的変更として扱われる。

**要件 R11.5**: バージョン指定はマイナー版まで（`"0.7"` = `>=0.7.0, <0.8.0`）とする。
次のマイナー版への追従は自動で行わず、明示的に上げる。

**要件 R11.6**: ch32rv のマイナー版を上げる際は、
**実機での識別動作を再確認してからでなければ取り込まない。**
CI には WCH-Link もターゲットボードも無く、検証できないためである。

**要件 R11.7**: `ch32rv-usb` による USB 列挙は、
**WCH-Link プローブを見つけて開くためだけに用いる。**
本アプリのデバイス一覧の情報源は `CfgMgr32` である（R11.1）。
2 つの列挙結果を突き合わせる際は、Instance ID を結合キーとする。

### 11.4 Rust の実装規律

**要件 R11.4**: ch32rv と同一の規律を適用する。

```toml
edition      = "2024"
rust-version = "1.88"

[lints.rust]
unsafe_code = "forbid"

[lints.clippy]
unwrap_used   = "deny"
expect_used   = "deny"
todo          = "deny"
unimplemented = "deny"
panic         = "deny"
```

`unsafe_code = "forbid"` は Windows API を直接呼ぶ都合と衝突しうる。
その場合は **FFI を行う crate を分離し、そこだけ `unsafe_code = "allow"` とする。**
アプリケーション層と識別ロジック層には unsafe を持ち込まない。

## 12. 配布とリリース

### 12.1 配布物

リリースごとに 2 種類を提供する。

```text
wsl-usb-identity-manager_<version>_x64_setup.exe     NSIS / per-user / 管理者権限不要
wsl-usb-identity-manager_<version>_x64_portable.zip  ポータブル（portable.txt 同梱）
```

**要件 R12.1**: MSI は提供しない。

> per-machine（MSI）と per-user（NSIS）が併存すると、
> 同じアプリが 2 箇所に入り、更新経路が二重化する。

**要件 R12.2**: 自動更新機構は実装しない。
更新は `winget upgrade` または ZIP の差し替えによる。

> 自己更新と WinGet が併存すると、winget 側の記録とインストール実体がずれる。
> また Tauri の updater は署名を必須とし、鍵を失うと以後の更新を配信できない。

**要件 R12.3**: WinGet には NSIS インストーラのみを登録する
（`InstallerType: nullsoft`）。ポータブル ZIP は GitHub Release で直接配布する。

> WinGet は `nullsoft` 指定時にサイレントインストールのスイッチを自動設定する。
> community repository はサイレント対応を必須としている。
> `zip` でも登録できるが `NestedInstallerType` の指定が要り、
> GUI アプリを WinGet の Links シムに置く形になる。

**要件 R12.9**: ポータブル ZIP は、ビルド成果の実行ファイルとリソースをまとめて作る。

> Tauri はポータブル形式を正式にはサポートしない。
> この ZIP は WebView2 が導入済みの環境向けであり、
> インストーラのようにブートストラッパを埋め込めない（§11.2）。

### 12.2 バージョン管理

**要件 R12.4**: バージョンの唯一の情報源は `Cargo.toml` の `version` とする。
`tauri.conf.json` に `version` を記述しない（Tauri は省略時に `Cargo.toml` を参照する）。

### 12.3 リリース手順

**要件 R12.5**: リリースは GitHub Actions の画面から `workflow_dispatch` で
手動起動する。タグ push によるリリースは行わない。

起動時に bump レベル（`major` / `minor` / `patch`）を指定する。
手順の詳細は [release.ja.md](release.ja.md) にある。

**要件 R12.6**: 変更点は開発時に `CHANGELOG.md` の `## Unreleased` に記載する。
リリース処理がバージョン番号を差し込み、その内容をリリース本文に転記する。

**要件 R12.7**: 同時実行によるバージョン競合を防ぐため、
ワークフローに `concurrency` を設定する。

**要件 R12.8**: bump コミットの push が必要なため、
既定ブランチの保護設定とワークフローの権限を整合させる。

## 13. 診断とエラー処理

### 13.1 前提条件の検査

**要件 R13.1**: 起動時に以下を検査し、満たさない場合は
**何が足りないか・どうすれば解決するかを示す**。黙って失敗しない。

| 検査項目 | 満たさない場合 |
| --- | --- |
| WebView2 Runtime の有無 | ダウンロード先を案内して終了（R11.2） |
| `usbipd.exe` の存在 | インストール手順を案内。デバイス一覧は表示可、usbipd 操作は無効化 |
| `usbipd` のバージョン | 5.x 未満なら警告。`state` の JSON 構造が異なる可能性を示す |
| `usbipd` サービスの稼働 | 起動方法を案内 |
| WSL の有無と Distribution | Attach 機能のみ無効化。他の機能は使える |

**要件 R13.2**: 前提条件を満たさない場合でも、
**満たしている範囲の機能は使えること。** 起動そのものを止めるのは WebView2 の欠落時のみ。

### 13.2 非同期操作の完了検知

`usbipd attach` などの操作は、コマンドの終了と実際の状態変化が一致しない。

**要件 R13.3**: 操作の成否は、コマンドの終了コードだけでなく
**`usbipd state` の再取得によって確認する。**

**要件 R13.4**: 状態変化の待機にはタイムアウトを設ける。
タイムアウトした場合は「操作は発行したが状態を確認できなかった」と表示する。
成功とも失敗とも断定しない。

**要件 R13.11**: 操作が失敗した場合も、状態を取得し直して表示を更新する。

> 失敗は「何も起きなかった」を意味しない。途中まで進んでいることもある。
> 表示を据え置けば、**エラーの隣に操作前の状態が残る**ことになり、
> 利用者はそれを操作後の状態として読む。

### 13.3 排他制御

**要件 R13.5**: 同一デバイスに対するプローブを同時に実行してはならない。
デバイス単位のロックを用いる（`ch32rv-usb` が同等の機構を持つ）。

**要件 R13.6**: プローブ実行中のデバイスに対する Attach / Bind 操作は
拒否するか、プローブ完了まで待機させる。
プローブ中に `bind --force` が走ると、プローブが途中で切断される。

**要件 R13.10**: 本アプリケーションの多重起動を許してはならない。
すでに起動している場合は、そのウィンドウを前面に出して終了する。

> 2 つ動いていれば、両方が `usbipd` を叩き、両方が自動 Attach の条件を実行する。
> 同じデバイスへの Attach が競合し、ユーザーが何もしていないのに片方が失敗する。
> 判定の単位はサインインセッションとする。設定ファイルも `Run` キーも
> ウィンドウも 1 ユーザーのものであり、
> 別のユーザーがサインインしたときは別のアプリとして動いてよい。

### 13.4 ログ

ハードウェアを操作するツールであり、
**問題の再現には現場のログが要る。**

**要件 R13.7**: 以下をファイルに記録する。

- 起動時に、本アプリの名前とバージョン
- デバイスの接続・切断イベント（Instance ID、LocationPath、時刻）
- プローブの実行と結果（対象、所要時間、成否）
- `usbipd` コマンドの実行内容と終了コード、`state` の差分
- 前提条件検査の結果

**要件 R13.8**: ログの出力先を UI から開けること。
ローテーションを行い、無制限に肥大しないこと。

**要件 R13.9**: ログに個人を特定しうる情報を含めない。
ユーザーが入力した Alias / Memo はログに出力しない。

| 自動 Attach（ボード ID / USB シリアル番号 / VID:PID / BUSID の条件） | §9 |

系統の追加がプローブの追加のみで完結する構造とする（R4.14）。

## 16. 想定する利用フロー

```text
USB デバイスを Windows へ接続
        ↓
本アプリが接続を検出（§8）
        ↓
USB Identity を取得（CfgMgr32）
        ↓
Transport として一覧に表示（VID/PID、シリアル、ポート、Windows 認識名）
        ↓
  ┌─ Target を識別できる系統 ──→ 「未識別」として表示
  │                                ユーザーが「識別」を押す → プローブ
  │                                （自動識別が有効なら接続直後に実行）
  │                                     ↓
  │                                Target を表示（切断まで保持。§4.2）
  │
  └─ それ以外 ────────────────→ Transport のみで扱う
                                    Alias / Memo で補う（§3.5）
        ↓
usbipd 状態を取得（usbipd state）
        ↓
ユーザー操作または自動 Attach で WSL へ Attach
        ↓
WSL 側で USB デバイスを認識
        ↓
WSL 内部の既存処理（udev / board-identify）が動作
        ↓
シンボリックリンクが生成される
        ↓
必要に応じて本アプリから WSL 側の状態を参照・表示
```
