# 識別ポリシー（設計方針）

*[English](identification-policy.md) | [日本語](identification-policy.ja.md)*

前提: [docs/research-findings.ja.md](research-findings.ja.md)

本書は「どのデバイスがどの物理個体なのか」をどう決めるかの設計方針を記す。
要件そのものは [requirements.ja.md](requirements.ja.md) §4 にある。

---

## 1. 解くべき問題

実測 F3 で確定した事実。

> Windows が提供する情報だけでは、シリアルを持たない CH340 が複数ある場合、
> 「どのポートに刺さっているか」以上のことは分からない。

したがって個体識別にはプローブ（対象への問い合わせ）が要る。
しかし実測 F8 の通り、プローブには副作用がある。

- `esptool` 系は DTR/RTS を操作するため **ファームウェアが再起動する**
- WCH-Link の attach は **ターゲットのコアを一時停止させる**
- プローブ中のシリアル出力は失われる

**「識別のためにプローブする」と「プローブしてはいけない」が正面から衝突する。**
本アプリの設計の中心は、この衝突をどう捌くかにある。

---

## 2. 基本方針

> **識別結果は「いま問い合わせて得た事実」に限る。
> 過去の結果から現在を推定しない。**

プローブが安全な瞬間は 2 つある。

1. **ユーザーが明示的に指示したとき** — 副作用を承知の上での操作
2. **デバイスが接続された直後** — まだ誰も使い始めていないため、リセットされても実害が少ない

この 2 つ以外では、**プローブを一切行わない。**

そして、プローブしていない対象については **識別結果を表示しない。**
過去の結果を再利用して「たぶんこれ」を出すことはしない。

### 2.1 キャッシュ照合を採らない理由

「ポート位置と VID/PID を記録しておき、次回はそれで照合すればプローブせずに済む」
という設計は成立しない。次の状況を検出できないためである。

```text
記録:    CH340-α（前回 port1）    CH340-β（前回 port2）
現在:    port1 に 1 台            port2 に 1 台
実際:    α と β を入れ替えた
```

現在のポート集合と記録されたポート集合が同一になるため、照合は両方「一致」と判定し、
**両方とも逆の名前を表示する。**
これは実装の欠陥ではなく、ポート位置しか手がかりがない以上の原理的な限界である
（[F3](research-findings.ja.md#f3-シリアル番号を持たないデバイスは-windows-側だけでは原理的に個体識別できない)）。

USB シリアル変換は、**USB 側が 1 バイトも変わらないまま別のボードへ繋ぎ替えられる。**
「前回このポート／このシリアルの先にあったボード」から今回のボードは導けない。

確信度（`confirmed` / `probable` 等）を添えて「たぶんこれ」と表示することもしない。

- 確信度は、**誤っている可能性を利用者の側へ押し付けるだけ**で、誤りを減らさない
- 表示された名前を、利用者はほぼ確実に「そのデバイス」として扱う
- 名前が出ている以上、「識別」を押す動機が生まれない

**誤った名前を自信を持って表示するくらいなら、何も表示しない方がよい。**
未識別と表示されていれば、必要なときに 1 回押せば済む（R4.19 の一括識別）。

この判断の結果として、**保存するのはユーザーが決めたことだけ**になった
（requirements.ja.md §7.1）。観測した事実は毎回観測し直す。

## 3. 識別の 2 経路

### 経路 1: USB シリアルによる Transport の識別（プローブ不要）

デバイスが USB シリアル番号を持つ場合、Instance ID の第 3 要素がそのまま
**その USB デバイス自身**の識別子になる。

```text
USB\VID_1A86&PID_55D3\5B5F090816            CH343
USB\VID_303A&PID_1001\70:04:1D:DA:86:F0     ESP32-S3 native USB（MAC がシリアル）
USB\VID_2341&PID_0043\8573531333335160D1C2  Arduino Uno
```

ESP32-S3 / C3 などのネイティブ USB 機種は、ボード自身が USB デバイスであるため
**この経路だけで完全に識別できる**（プローブが要るのは CH340 等を介した旧 ESP32）。

一方 CH343 や WCH-Link のシリアルは **アダプタ／プローブ自身**を指す。
その先のボードについては何も語らない（requirements.ja.md §1.2）。

→ **シリアルは Transport の識別子として表示し、Target の識別子として扱わない**（R4.1）。

### 経路 2: プローブによる Target の識別（副作用あり）

アダプタやプローブの先にあるボードを知る唯一の方法。実行契機は §5 に限る。

## 4. 識別結果の寿命

識別結果は **そのデバイスが接続されている間だけ**保持する（R4.3）。

| 出来事 | 識別結果 | 理由 |
| --- | --- | --- |
| WSL へ Attach / Detach | **保持する** | ケーブルの先は変わっていない |
| アプリの再起動 | 破棄される | 保存しないため |
| **物理的な取り外し** | **破棄する** | 先が変わりうる唯一の瞬間 |

取り外しは、USB 側に何の痕跡も残さずにケーブルの先が入れ替わりうる唯一の瞬間である。
それを跨いで識別結果を持ち越せば、**事実の顔をした推測**になる。

UI は識別済みと未識別を区別して示す（R4.4）。
未識別は「調べていない」であって「不明な機器」ではない。

## 5. プローブの優先順位

複数の系統に対応すると、1 つのデバイスに複数のプローブが当てはまりうる。
WCH-Link はシリアルポートを持つため、汎用のシリアルプローブから見ると
**ESP32 を繋いだアダプタと区別がつかない。**

そこで各プローブは、自分が対象を **VID/PID で特定できるか**を宣言する（R4.17）。

| 種別 | 意味 | 例 |
| --- | --- | --- |
| 識別子による特定 | VID/PID でハードウェアが判る。何も触らずに判定できる | CH32 系（WCH-Link） |
| フォールバック | 形が合うだけ。先に何があるかは問い合わせるまで判らない | ESP32 系（COM ポート） |

識別子で特定できるプローブが対象を自分のものと認めたなら、
フォールバックのプローブは実行しない（R4.18）。
「認めた」には、実行できない状態（ARM モードの WCH-Link 等）も含む。
**ARM モードであっても WCH-Link であることに変わりはなく、
ESP32 用のリセットと同期信号を送ってよい相手ではない。**

> **フォールバック側に除外リストを持たせてはならない。**
> 「ESP32 プローブが除外する VID/PID」として表現すると、
> 系統が増えるたびにその除外リストが伸びる。
> 優先順位で表現すれば、新しい系統は自分の VID/PID を名乗るだけで済む。

## 6. プローブの実行契機

### 6.1 明示的プローブ

デバイス一覧および詳細画面の **「識別」ボタン**。

- 押した瞬間にプローブを実行する
- 副作用（ボードが再起動する等）を実行前に提示する。提示の省略は設定で選べる
- 接続中の未識別デバイスを**まとめて識別する**操作も提供する（R4.19）

一括識別は、自動識別の対象から外れるもの（シリアルを持つアダプタ、WCH-Link）を
利用者が 1 操作で拾うための手段である。

### 6.2 接続直後の自動識別

USB 接続イベントから一定時間内に限り、自動でプローブする（既定で有効）。

**根拠**: 挿した直後のボードはまだ使われていないことが多く、
リセットされても実害が出にくい。

| 項目 | 既定値 | 説明 |
| --- | --- | --- |
| 自動識別 | 有効 | 機能全体の ON/OFF |
| 対象 | シリアルを持たないデバイスのみ | シリアル持ちは経路 1 で足りることが多いため |
| 猶予時間 | 接続イベントから 10 秒以内 | これを過ぎたら自動実行しない |
| 除外する VID/PID | ユーザーが列挙（既定は空） | 触られては困る機器を名指しする |

**既定で有効にする理由**: 識別結果を保存しない以上、
挿すたびに手で押させるのでは実用に耐えない。
副作用が最も小さい瞬間に自動で済ませ、
触ってほしくない対象は利用者が名指しできるようにする。

**除外リストであって許可リストではない理由**: CH340 の VID/PID は、
その先が開発ボードかルータのコンソールかを何も語らない。
許可リストを作れば結局よく使われるブリッジを全て並べることになり、
除外リストと同じ効果を回りくどく実現するだけである。

#### 猶予時間内の再試行

デバイスが Windows に見えてから COM ポートが割り当てられるまでには間がある。
到達した瞬間に 1 度だけ判定すると、自動識別はたいてい負ける。
**猶予時間内はプローブ可能になるまで再試行する**（R4.20）。
試行の上限を与えるのは猶予時間であって、最初の 1 回ではない。

### 6.3 プローブを行わない場面（禁止事項）

- 定期ポーリング
- 一覧画面の更新
- アプリ起動時の一括スキャン
- 自動 Attach の判定のため

### 6.4 同時実行

**同一デバイスへのプローブを同時に走らせない。**
また、一括識別は 1 台ずつ順に行う。
2 つのプローブが同じアダプタを奪い合うことになり、
どちらも失敗するか、片方が途中で切断される。

## 7. 具体的なシナリオ

### CH340 が 3 個、それぞれ別のボードに繋がっている

**挿したとき**

1. 3 個とも Transport として一覧に出る（`VID_1A86&PID_7523`、ポートのみ相違）
2. シリアルを持たないため、自動識別の対象になる
3. 1 台ずつ順にプローブが走り、`esp32-7cdfa1123456` 等が確定する
4. Target 列に識別結果が出る。**デバイス名は Windows の認識名のまま**（R10.7）

**自動識別を切っている場合**

1. 3 個とも「未識別」と表示される
2. 行の「識別」ボタン、または一括識別で確定する

**ポートを入れ替えた場合**

一度抜いた時点で識別結果は破棄される。挿し直せば、それは新しい未識別のデバイスであり、
再度識別すれば正しい答えが出る。**入れ替えを検出する必要がそもそも無い。**

### ESP32-S3（ネイティブ USB）

シリアル（MAC）を持ち、ボード自身が USB デバイスであるため、
Transport の識別がそのまま Target の識別になる。**一度もプローブしない。**

### WCH-Link に CH32V305 を繋いでいる

1. WCH-Link はシリアルを持つため、自動識別の対象外になる
2. Target 列は「未識別」。CH32 プローブが利用可能として示される
3. 「識別」を押すと、プローブがターゲットのコアを止めて部品 UUID を読み、
   `<チップ種別>-<部品 UUID>` の形の識別子が確定する
4. WCH-Link が ARM モードの場合は、切り替えが必要である旨を示す。
   **アプリはモードを切り替えない**（R4.15）
