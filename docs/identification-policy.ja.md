# 識別ポリシー（設計方針）

作成日: 2026-09-02
前提: [docs/research-findings.ja.md](research-findings.ja.md)

---

## 1. 出発点

調査 F3 で確定した事実。

> Windows が提供する情報だけでは、シリアルを持たない CH340 が複数ある場合、
> 「どのポートに刺さっているか」以上のことは分からない。

したがって個体識別にはプローブ（対象への問い合わせ）が要る。
しかし調査 F8 の通り、プローブには副作用がある。

- `esptool` 系は DTR/RTS を操作するため **ファームウェアが再起動する**
- WCH-Link の attach は **ターゲットのコアを一時停止させる**
- プローブ中のシリアル出力は失われる

**したがって「識別のためにプローブする」と「プローブしてはいけない」が正面から衝突する。**
本アプリの設計の中心は、この衝突をどう捌くかにある。

---

## 2. 基本方針

> **プローブは「いつでも安全ではない」が「安全な瞬間はある」。
> その瞬間を狙い、それ以外はキャッシュで済ませる。**

安全な瞬間は 2 つある。

1. **ユーザーが明示的に指示したとき** — 副作用を承知の上での操作
2. **デバイスが接続された直後** — まだ誰も使い始めていないため、リセットされても実害が少ない

この 2 つ以外では、**プローブを一切行わない。**

---

## 3. 識別の 3 経路

### 経路 1: USB シリアルによる識別（プローブ不要）

デバイスが USB シリアル番号を持つ場合、Instance ID の第 3 要素がそのまま個体識別子になる。

```text
USB\VID_1A86&PID_55D3\5B5F090816            CH343
USB\VID_303A&PID_1001\70:04:1D:DA:86:F0     ESP32-S3 native USB（MAC がシリアル）
USB\VID_2341&PID_0043\8573531333335160D1C2  Arduino Uno
```

この場合、**前回の識別結果をキャッシュから復元するだけでよく、プローブは一切不要**。
ポートを差し替えても、再起動しても、同じシリアルなら同じデバイスである。

ESP32-S3 / C3 などのネイティブ USB 機種は MAC アドレスがシリアルになるため、
**この経路だけで完全に識別できる**（プローブが必要なのは CH340 等を介した旧 ESP32 のみ）。

→ **シリアルを持つデバイスは、原則としてプローブしない。**

### 経路 2: キャッシュ照合（プローブ不要）

シリアルを持たないデバイスは、以下のヒントを組み合わせて登録済みデバイスと照合する。

- `LocationPaths`（物理ポート、F2）
- VID / PID
- 直前の切断からの経過時間
- 同一 VID/PID の他候補が同時に存在するか

候補が一意に定まれば、**プローブせずに登録済みの Identity を復元する。**

### 経路 3: プローブによる識別（副作用あり）

経路 1・2 で決まらないときのみ。実行契機は §2 の 2 つに限る。

---

## 4. 確信度モデル

各デバイスは常に「確信度」を持ち、UI と自動処理の判断材料になる。

| confidence | 根拠 | プローブ | 自動 Attach |
| --- | --- | --- | --- |
| `confirmed` | Application Identity 一致、または USB シリアル一致 | 不要 | 可 |
| `probable` | ポート位置 + VID/PID が登録と一致し、競合候補なし | 不要 | 設定次第 |
| `ambiguous` | 同一 VID/PID の候補が複数 / 位置が変わった | 要（ユーザー操作） | **不可** |
| `unknown` | 未登録 | 要（ユーザー操作） | 不可 |

UI 上でも確信度を明示する。
「たぶんこれ」を「これ」と偽らないことが、この設計の要点である。

---

## 5. 確信度の判定アルゴリズム（暫定）

> **本節は暫定仕様である。**
> 実装後に実機で触りながら調整することを前提とし、
> 調整が §5.5 の範囲に閉じる構造を要件とする。

### 5.1 なぜアルゴリズムとして書く必要があるか

§4 の表を素朴に「デバイスごとに照合する」と読むと壊れる。

```text
登録済み:  CH340-α（前回 port1）    CH340-β（前回 port2）
現在:      port1 に 1 台             port2 に 1 台
実際:      α と β を入れ替えた
```

デバイス個別に照合すると、port1 のデバイスは α と一致し、port2 のデバイスは β と一致する。
両方 `probable` になり、**両方とも逆の名前を表示する。**

**したがって判定は「デバイス単体」ではなく「同一 VID/PID の集合」を単位に行う。**

### 5.2 入力と出力

```text
入力:
  現在デバイス集合 D   各要素 = (vid, pid, serial?, location_path, instance_id)
  登録済み集合     R   各要素 = (identity_key, vid, pid, usb_serial?,
                                hints{ last_location_path, last_seen_at, ... })

出力:
  [(device, identity?, confidence)]  D の各要素に対して 1 件
```

### 5.3 手順

#### Step 1 — シリアルによる束縛

`d.serial` が非空で `r.usb_serial == d.serial` となる `r` があれば束縛する。

- confidence = **`confirmed`**
- 束縛した `d` と `r` は以降の手順から除外する
- ポート位置は一切参照しない（シリアルはポートより強い）

#### Step 2 — グループ化

残りを `(vid, pid)` でグループ化する。
グループ `G` は、未束縛の現在デバイス `D_g` と未束縛の登録済み `R_g` からなる。

#### Step 3 — グループ内のポート照合

`D_g` の各 `d` について、`r.hints.last_location_path == d.location_path` となる
`r ∈ R_g` を探す。1:1 で成立したものを「ポート一致」とする。

判定は以下とする（**暫定・案 Z**）。

```text
ポート一致した d
  かつ その位置が他の r の last_location_path と衝突していない
    → probable

ポート一致しなかった d
  その位置が どの r の last_location_path でもない（純粋な新規出現）
    → 他のデバイスに影響を与えない
    → 未束縛のまま Step 4 へ

  その位置が 他の r の last_location_path と一致する（移動の可能性）
    → その位置に関係する d と r を全て ambiguous に落とす
```

**この案を選ぶ理由**: 実運用では「4 台のうち 1 台だけ新しく挿した」が最も多い。
グループ内に 1 つでも不一致があれば全員を落とす案（案 X）は安全側だが過剰で、
既存 3 台まで毎回 `ambiguous` になり実用にならない。
一方、一致した分だけ無条件に `probable` にする案（案 Y）は、
**移動によって別デバイスの記憶ポートを踏んだ場合に誤認する。**
案 Z は「衝突が起きた箇所だけ広く落とす」折衷である。

#### Step 4 — 残り

未束縛のまま残った `d` は **`unknown`** とする。

#### Step 5 — Application Identity による昇格

プローブ済みで `application_identity` が登録済みのものと一致した場合、
ポート位置に関係なく **`confirmed`** に昇格する。

### 5.4 原理的に検出できないケース

> **2 台が互いのポートを完全に入れ替えた場合、本アルゴリズムは検出できない。**

現在のポート集合と記憶されたポート集合が同一になるため、
Step 3 は全て「ポート一致」と判定し、両方 `probable` になる。
そして **両方とも誤った名前を表示する。**

これはアルゴリズムの欠陥ではなく、**ポート位置しか手がかりがない以上の原理的限界**である
（[research-findings.ja.md F3](research-findings.ja.md#f3-シリアル番号を持たないデバイスは-windows-側だけでは原理的に個体識別できない)）。

対処は仕様として以下とする。

- **`probable` は「確定ではない」ことを UI 上で明示する**（要件 R4.3）
- 入れ替えの可能性がある操作をした自覚があるユーザーが、
  「識別」を押せば `confirmed` に解決できる導線を常に用意する
- 自動 Attach の既定を `confirmed` のみとし、
  `probable` を含めるかどうかをユーザーの判断に委ねる（要件 R9.3）

### 5.5 調整が想定される箇所

実機で触った後に変更しうる箇所を、あらかじめここに列挙しておく。
**変更がここに閉じることを構造要件とする。**

| # | 調整点 | 暫定値 |
| --- | --- | --- |
| T1 | Step 3 の判定方針 | 案 Z（衝突箇所のみ落とす） |
| T2 | グループ化のキー | `(vid, pid)` |
| T3 | `location_path` の一致判定 | 完全一致 |
| T4 | `last_seen_at` を判定に使うか | 使わない |
| T5 | 純粋な新規出現を `probable` に含めるか | 含めない（`unknown`） |
| T6 | `confirmed` への昇格条件 | シリアル一致 または Application Identity 一致 |

T3 について補足する。ハブを別のポートに挿し直すと `location_path` の途中が変わるため、
完全一致では不一致になる。末尾のポート番号のみを見る、
ハブの手前までを別扱いにするなどの緩和が考えられるが、
**緩和すると別のハブの同じポート番号を同一視する危険がある。**
暫定では完全一致とし、実機での使い勝手を見て判断する。

### 5.6 構造要件

**要件 P5.1**: §5.3 の判定を、**副作用を持たない単一の関数**として分離する。

```text
resolve(D: 現在デバイス集合, R: 登録済み集合) -> [(device, identity?, confidence)]
```

- I/O を行わない（デバイスに触らない、ファイルを読まない、時刻を取得しない）
- 判定に必要な値は全て引数で受け取る
- テーブル駆動テストで検証できること

**要件 P5.2**: §5.5 の調整が、この関数の内部変更のみで完結すること。
呼び出し側や永続化スキーマの変更を伴わないこと。

**要件 P5.3**: §5.1 と §5.4 のケースを回帰テストとして保持する。
特に「完全な入れ替えは検出できない」ことを、
**期待される挙動としてテストに書く**（将来の改変で暗黙に壊さないため）。

## 6. プローブの実行契機

### 6.1 明示的プローブ（既定で有効）

デバイス一覧および詳細画面の **「識別」ボタン**。

- 押した瞬間にプローブを実行する
- 副作用（ボードが再起動する等）を実行前に明示する
- `ambiguous` / `unknown` のデバイスでは、ボタンを目立たせる

### 6.2 接続直後の自動識別（オプション、既定で無効）

USB 接続イベントから一定時間内に限り、自動でプローブしてよいとする設定。

**根拠**: 挿した直後のボードはまだ使われていないことが多く、
リセットされても実害が出にくい。

設定項目（案）:

| 項目 | 既定値 | 説明 |
| --- | --- | --- |
| 自動識別 | 無効 | 機能全体の ON/OFF |
| 対象 | シリアルを持たないデバイスのみ | シリアル持ちは経路 1 で足りるため対象外 |
| 猶予時間 | 接続イベントから 10 秒以内 | これを過ぎたら自動実行しない |
| 対象 VID/PID | ユーザーが列挙 | 未知のデバイスに無条件送信しない（R4.9） |
| 確信度の下限 | `ambiguous` 以下のみ | すでに確定しているものは触らない |

**この機能を既定で無効にする理由**: 副作用のある動作を、
ユーザーが明示的に許可していない状態で走らせるべきではないため。

### 6.3 プローブを行わない場面（禁止事項）

- 定期ポーリング
- 一覧画面の更新
- アプリ起動時の一括スキャン
- 自動 Attach の判定のため

## 7. キャッシュの構造

```text
Identity（永続）
  identity_key        確定した識別子（§4.5 の形式。本アプリ内部の識別子）
                        例: esp32-s3-7cdfa1123456
  usb_serial          あれば。経路 1 の照合キー
  vid / pid
  application_identity  プローブで得た情報（Device ID / Type / Rev / FW）
  user_metadata       Alias / Memo / Tags / Default WSL / Auto Attach

Hints（学習・更新される）
  last_location_path  最後に見た物理ポート（F2）
  last_instance_id    最後に見た Instance ID（usbipd との結合キー、F4）
  last_com_port       参考表示用（永続的な識別には使わない）
  last_seen_at
  probe_result_at     最後にプローブした日時
```

**永続化してはならないもの**（調査 F1 より）:

- BUSID
- COM 番号を識別子として（表示用の参考値としては保持してよい）
- `/dev/ttyUSB*` などの Linux デバイスノード

## 8. 具体的なシナリオ

### CH340 が 3 個、それぞれ別のボードに繋がっている

**初回登録**

1. 3 個とも `unknown` として一覧に出る（`VID_1A86&PID_7523`、ポートのみ相違）
2. ユーザーが 1 個ずつ「識別」を押す
3. プローブが走り、それぞれ `esp32-7cdfa1123456` 等が確定する
4. ユーザーが Alias（「会議室 CO2 センサー」等）を付ける
5. ポート位置がヒントとして記録される

**2 回目以降（同じポートに挿す）**

1. 接続イベント → ポート位置 + VID/PID で照合 → 一意に定まる
2. `probable` として Alias を表示。**プローブは走らない**
3. 自動 Attach 設定があればそのまま Attach

**ポートを入れ替えた場合**

1. 照合結果が競合 → 3 個とも `ambiguous`
2. Alias は出すが「未確認」を明示し、**自動 Attach は行わない**
3. ユーザーが「識別」を押せば確定し、ヒントが更新される

### ESP32-S3（ネイティブ USB）

シリアル（MAC）を持つため、初回から `confirmed`。**一度もプローブしない。**
